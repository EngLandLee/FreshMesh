# Git, CI, release, and Pages workflow

This document describes the repository automation as it is configured in source.
It does **not** claim that branch protection, required checks, or human reviews
are enabled on GitHub. A maintainer must inspect the repository settings before
relying on any of those controls.

## Issues, branches, and pull requests

* Use the existing issue forms for a bug, feature, or documentation/license
  correction. Do not put credentials, private customer data, or exploitable
  details in a public issue; follow [SECURITY.md](../SECURITY.md) for a private
  report.
* Work on a focused branch created from the intended target branch. Use a short,
  imperative commit subject and keep unrelated formatting out of the branch.
  Branch names should make the intent clear, such as `fix/receipt-quantity` or
  `docs/release-process`; do not work directly on `main`.
* A pull request must explain the behavior change, security impact, test/evidence
  run, and any dependency or license change. Link the issue when one exists.
  Runtime, container, workflow, or browser changes should include the real Docker
  and browser evidence, not only a unit-test result.
* Automation is a gate, not an approval. A green check does not replace a
  maintainer's review of authorization, tenant isolation, workflow transitions,
  data retention, licensing, or the proposed release surface. CODEOWNERS requests
  ownership review, but its presence does not prove that protection is enabled or
  that a review occurred.

## Pull-request and main CI

The following workflow job IDs are intentionally stable. If repository settings
later make checks required, use these exact job IDs (with their workflow names)
when selecting checks; do not infer that they are currently required.

| Workflow | Job ID | Purpose |
| --- | --- | --- |
| `unit.yml` | `unit` | uv-locked backend tests, Ruff, portal syntax, Compose model, and strict license/source audit |
| `license.yml` | `audit` | strict source-boundary/header check and shellcheck for release scripts |
| `docker-e2e.yml` | `e2e` | a real Docker stack, HTTP business flow, multi-role Playwright captures, and static-site check |
| `sbom.yml` | `sbom` | standalone manually/release-published SBOM action |
| `release.yml` | `release` | trusted tag verification, real-stack gates, source archive, checksums, SBOMs, and release assets |
| `release.yml` | `pages` | calls the Pages workflow only after the release payload is verified |
| `pages.yml` | `build` / `deploy` | checks or receives the selected static site, then uploads and deploys Pages |

`unit` and `audit` run for pull requests and pushes to `main`. `e2e` runs for
pull requests, pushes to `main`, and manual dispatch. Pull-request jobs have
read-only repository permissions and do not deploy, publish a release, or write
Pages. The E2E job uses a run-specific Compose project name, fresh volumes, and
always removes only that named project.

E2E also runs `make screenshots`, `make site`, serves `dist/site` on port 3181,
and runs `make site-check`. The `e2e-evidence-<run-id>` artifact contains the
captured browser evidence and built site when those files exist; it is diagnostic
CI evidence, not a substitute for release provenance.

## Releases

A release is created only by pushing an immutable tag matching exactly
`vMAJOR.MINOR.PATCH`, for example `v0.3.0`. The release workflow checks out the
complete tag history and verifies that both `HEAD` and the tag resolve to the
`GITHUB_SHA` that triggered the run. It installs Python 3.12, uv, Node.js 22,
locked dependencies, and Chromium; then it runs `make verify` before starting the
actual Docker stack.

The release gate uses a run-specific Compose project and fresh synthetic volumes.
It waits for `http://localhost:3180/api/health`, runs `make demo-check`, captures
`make screenshots`, builds `make site`, serves/checks the site on port 3181, and
only then runs `make release VERSION=<tag-without-v>`. The release job also runs
an independent Syft CycloneDX scan over the source archive. Its separate SBOM is
not a replacement for `dist/sbom.cdx.json` generated by the release script.

The GitHub release contains, at minimum:

* `freshmesh-dxos-v<version>-source.tar.gz`;
* `SHA256SUMS`, the release-script SBOM, and the independent Syft source SBOM;
* every screenshot PNG, its `.license` sidecar, `screenshots.json`, and the
  screenshot `LICENSE` ledger; and
* `website/assets/banner.png` and its sidecar only when that optional original
  PNG exists.

The original banner SVG remains source in the repository. The archive is made
from tracked first-party source and excludes `dist/`, virtual environments,
`node_modules`, runtime volumes, data, secrets, credentials, and generated output.
The clean-source gate rejects tracked changes and untracked files before
packaging. New source/configuration/documentation files use the Apache-2.0 SPDX
notice and the 2026 FreshMesh-DXOS copyright notice. JSON files require their
`.license` sidecar where the source audit requires it; captured images require a
sidecar and ledger entry. Never add a mock screenshot, copied reference-project
asset, secret, or unlicensed binary to a release.

The release job has `contents: write` only for the trusted tag job. Its release
publisher is conservative when a release with the same tag already exists: it
keeps existing assets and uploads only missing assets; it does not delete a
release, move a tag, or overwrite an asset. The Pages job receives only the
verified `dist/site` artifact from that same run. The standalone `sbom.yml`
workflow remains available for manual or published-release SBOM work; the real
tag workflow performs its own Syft scan so GitHub's suppression of workflows
triggered by a `GITHUB_TOKEN` release publication cannot omit the release SBOM.

## Pages

`pages.yml` is both a reusable `workflow_call` workflow and a manual
`workflow_dispatch` workflow. The tag release calls it explicitly after the
release job succeeds, rather than waiting for a `release` event. The called job
downloads the release run's exact checked `dist/site` artifact and deploys that
payload. It does not rebuild or silently replace the verified tag site.

A maintainer can manually dispatch Pages and select a branch, tag, or SHA. With
no verified caller artifact, the workflow checks out that selected ref, runs
`make site`, serves it on port 3181, and runs `make site-check` before uploading
Pages. `make site` uses local captures when present; otherwise its versioned
GitHub release URLs fetch the existing verified v0.3.0 image assets. If those
assets do not exist, the build fails rather than inventing screenshots. The
selected ref—not the default branch—is therefore the source of the manual
publication.

Pages is a static introduction at
`https://englandlee.github.io/FreshMesh-DXOS/`. It is not the hosted business
application and does not provide a public API, Keycloak tenant, database,
workflow engine, or demo credentials. The application remains a local Docker
stack at `http://localhost:3180`; run it from source when an interactive business
flow is needed. The Pages workflow grants read access for source, Pages write
access for the payload, and an OIDC ID token only to the deployment job.

## Recovery and rollback

If a tag run fails before publication, fix the branch, create a new commit, and
use a new SemVer tag. Do not force-move a published tag. If a release exists but
is missing assets, rerun the same tag workflow only after confirming the tag still
resolves to the intended commit; the publisher preserves existing assets and
adds missing ones. If a generated asset is incorrect, stop publication, create a
new patch tag, and explain the supersession in its release notes instead of
silently replacing the old artifact.

If Pages fails after the release is complete, rerun the Pages workflow with the
published tag selected. It will use the existing verified v0.3.0 image assets
when a caller artifact is unavailable. To roll back Pages, manually dispatch the
workflow at the last known-good tag/SHA and confirm the deployed URL; this rolls
back the static introduction only and does not roll back running application
containers or database state. Stop a local stack with `docker compose down`
without `-v`, preserving its business data. Only disposable CI projects created
by this run are removed with `down -v`; never remove another developer's or
workflow's project.
